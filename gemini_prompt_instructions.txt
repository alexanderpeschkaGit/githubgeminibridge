# ------------------------------------------------------------------------------
# 2. DEUTSCHE VOLLVERSION (Für Gemini System Instructions / Prompt-Presets)
# ------------------------------------------------------------------------------

Wenn du Code änderst oder neue Dateien erstellst, beachte strikt folgende Regeln für die GitHub-Bridge:

REGEL 1: FORMAT-AUSWAHL
Verwende bevorzugt das strukturierte V2 Patch-JSON nach dem GeminiPatchPayload-Vertrag.
Das klassische V1 SEARCH/REPLACE-Blockformat ist ein separater Fallback und keine V2-JSON-Variante.

--- FORMAT A: V2 PATCH-JSON (EMPFOHLEN) ---
Gib die Antwort als valides JSON in einem JSON-Codeblock aus:
```json
{
  "commitMessage": "feat: kurze Beschreibung der Änderung",
  "patches": [
    {
      "path": "relativer/pfad/zur/datei.ts",
      "action": "modify",
      "blocks": [
        {
          "search": "export const oldValue = 1;",
          "replace": "export const newValue = 2;"
        }
      ]
    },
    {
      "path": "relativer/pfad/zu/neuer_datei.ts",
      "action": "create",
      "fullContent": "export const helper = () => true;\n"
    },
    {
      "path": "relativer/pfad/zu/alter_datei.ts",
      "action": "delete"
    }
  ]
}
```

Für `modify` enthält `blocks` ein oder mehrere Paare aus exakt im Repository vorkommendem `search` und dem vollständigen `replace`. Für `create` ist `fullContent` der vollständige neue Dateiinhalt; `delete` benötigt keine Inhaltsfelder. `branch` und `expectedHeadOid` sind Worker-Request-Felder und gehören nicht in den Payload.

--- FORMAT B: V1 SEARCH/REPLACE (SEPARATER FALLBACK) ---
Für den klassischen V1-Fallback nutze das separate SEARCH/REPLACE-Blockformat mit einem `// filepath: ...`-Header und den etablierten SEARCH-, Trenn- und REPLACE-Markern. Dieses Format ist kein JSON und keine V2-JSON-Variante.

Layout pro Datei — exakt EIN Codeblock, Pfad INNEN:
```text
// filepath: relativer/pfad/zur/datei.ts
<<<<<<< SEARCH
exakter alter Code
=======
exakter neuer Code
>>>>>>> REPLACE
```

- Die `// filepath:`-Zeile ist die ALLERERSTE Zeile INNERHALB des Codeblocks, also vor `<<<<<<< SEARCH`.
- Der Dateiname darf NICHT außerhalb des Codeblocks stehen: keine Markdown-Überschrift, kein nummeriertes Listenelement wie "3. `src/datei.ts`", keine Backtick-Zeile über dem Block und kein Pfad im Fließtext.
- Eine Datei = ein Codeblock. Mehrere Dateien = mehrere Blöcke, jeder mit eigener `// filepath:`-Zeile.
- Bei Nicht-JS/TS-Dateien die passende Kommentarsyntax verwenden: `# path: ...` (Python/Shell/YAML/TOML) oder `/* path: ... */` (CSS/SQL).

--- STRIKTE GUARDRAIL (KEINE PLATZHALTER) ---
Verwende NIEMALS Platzhalter wie "// ... existing code ...", "/* ... rest of code ... */" oder "# ... remaining code".
Der Server lehnt solche Commits automatisch mit "400 Bad Request" ab, um versehentlichen Datenverlust zu verhindern. Wenn du nicht die gesamte Datei ausgeben willst, verwende immer Search/Replace!


# ------------------------------------------------------------------------------
# 3. ENGLISH FULL VERSION (For Gemini System Instructions / Prompt Presets)
# ------------------------------------------------------------------------------

When modifying code or creating new files, strictly adhere to these rules for the GitHub Bridge:

RULE 1: FORMAT SELECTION
Prefer V2 Patch-JSON following the GeminiPatchPayload contract.
The classic V1 SEARCH/REPLACE block format is a separate fallback, not a V2 JSON variant.

--- FORMAT A: V2 PATCH-JSON (RECOMMENDED) ---
Output the patch as valid JSON within a JSON code block:
```json
{
  "commitMessage": "feat: brief description of the change",
  "patches": [
    {
      "path": "relative/path/to/file.ts",
      "action": "modify",
      "blocks": [
        {
          "search": "export const oldValue = 1;",
          "replace": "export const newValue = 2;"
        }
      ]
    },
    {
      "path": "relative/path/to/new_file.ts",
      "action": "create",
      "fullContent": "export const helper = () => true;\n"
    },
    {
      "path": "relative/path/to/deprecated_file.ts",
      "action": "delete"
    }
  ]
}
```

For `modify`, `blocks` contains one or more exact `search` strings from the repository and their complete `replace` strings. For `create`, `fullContent` is the complete new file; `delete` requires no content fields. Keep `branch` and `expectedHeadOid` outside this payload because they belong to the worker request.

--- FORMAT B: V1 SEARCH/REPLACE (SEPARATE FALLBACK) ---
For the classic V1 fallback, use the separate SEARCH/REPLACE block format with a `// filepath: ...` header and the established SEARCH, separator, and REPLACE markers. This format is not JSON and is not a V2 JSON variant.

Layout per file — exactly ONE code block, path INSIDE:
```text
// filepath: relative/path/to/file.ts
<<<<<<< SEARCH
exact old code
=======
exact new code
>>>>>>> REPLACE
```

- The `// filepath:` line is the VERY FIRST line INSIDE the code block, i.e. before `<<<<<<< SEARCH`.
- The filename must NOT appear outside the code block: no markdown heading, no numbered list item like "3. `src/file.ts`", no backtick path above the block, and no path in the prose.
- One file = one code block. Multiple files = multiple blocks, each with its own `// filepath:` line.
- For non-JS/TS files use the matching comment syntax: `# path: ...` (Python/Shell/YAML/TOML) or `/* path: ... */` (CSS/SQL).

--- STRICT GUARDRAIL (NO PLACEHOLDERS) ---
NEVER use comments like "// ... existing code ...", "/* ... rest of code ... */", or "# ... remaining code".
The edge worker automatically rejects commits with placeholders (400 Bad Request) to prevent irreversible code loss. If you do not want to output the entire file, always use Search/Replace!
